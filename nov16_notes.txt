# CashIQ – Complete Implementation Change Log
**Project:** AI-Powered Business Finance Management System  
**Update:** ML Architecture Overhaul & Adaptive Anomaly Detection  
**Date:** 16 November 2026

## 1. Overview

CashIQ underwent a significant machine learning architecture upgrade. The primary objective was to move from basic amount-based anomaly detection to a context-aware, adaptive ML system capable of understanding individual business spending patterns.

The update introduced:
- Context-aware anomaly detection.
- Dynamic behavioural learning.
- Human-in-the-loop feedback.
- An 11-component modular ML architecture.
- Model evaluation, registry and monitoring.
- Frontend integration for anomaly review and feedback.

## 2. Anomaly Detection Improvements

### 2.1 Context-Aware Detection

The previous implementation relied heavily on global Z-score and IQR calculations, which could flag legitimate transactions simply because their amounts differed significantly.

The new implementation introduces:
- Category-specific spending baselines.
- Separate income and expense analysis.
- Merchant-based behavioural analysis.
- Transaction frequency and velocity analysis.
- Temporal features, including day of week and weekend indicators.
- Multivariate Isolation Forest.

Transactions are now evaluated using contextual features rather than transaction amount alone.

### 2.2 Ten-Dimensional Feature Engineering

A 10-dimensional feature vector was introduced, incorporating:

1. Log-transformed transaction amount.
2. Category-relative spending ratio.
3. Category-specific Z-score.
4. Transaction-type spending ratio.
5. Merchant novelty score.
6. Merchant-relative amount ratio.
7. Seven-day transaction velocity.
8. Day-of-week sine encoding.
9. Day-of-week cosine encoding.
10. Weekend indicator.

### 2.3 Explainable Anomaly Detection

The detector now provides:
- Anomaly scores.
- Severity classifications.
- Structured explanations.
- Identification of unusual spending amounts, merchant novelty, frequency spikes and temporal mismatches.

### 2.4 Dynamic and Adaptive Learning

A feedback-based learning mechanism was introduced.

Users can classify flagged transactions as:
- Legitimate.
- Suspicious.

Confirmed feedback is stored as ground truth and used to update behavioural profiles.

Additional improvements:
- Rolling statistical updates.
- Bounded behavioural adaptation.
- Category-specific spending profile updates.
- Prevention of repeated alerts for reviewed legitimate transactions.
- Controlled retraining when sufficient verified data accumulates.

Example: If a business initially purchases a $10 domain and subsequently purchases a $10,000 server, the system can learn from user confirmation that such technology expenditure is legitimate.

### 2.5 Cold-Start Handling

The system introduces conservative benchmark-based thresholds when historical category data is insufficient.

This helps new businesses receive anomaly assessments without requiring extensive historical transaction records.

## 3. Complete ML Application Architecture

A modular architecture consisting of 11 logical components was introduced.

| Component | Responsibility |
|---|---|
| 1. Data Collector | Collects and standardizes transaction data. |
| 2. Ground-Truth Collector | Stores user-confirmed labels and feedback. |
| 3. Labelizer | Maintains verified and predicted transaction labels. |
| 4. Feature Transformer | Cleans, preprocesses and transforms transaction data. |
| 5. ML Orchestrator | Coordinates inference, training and feedback. |
| 6. Model Builder | Builds categorization, anomaly detection and forecasting models. |
| 7. Evaluator | Evaluates model performance using ML metrics. |
| 8. Model Registry | Tracks model versions and evaluation metadata. |
| 9. Monitoring | Tracks behavioural drift and false-positive rates. |
| 10. Model Serving | Exposes prediction and scanning functionality. |
| 11. Frontend Integration | Displays ML results and collects user feedback. |

### ML Data Flow

Transaction Sources → Data Collector → Ground-Truth Collection & Labelization → Feature Transformation → ML Orchestration → Model Building & Evaluation → Model Registry & Monitoring → Model Serving → CashIQ Frontend.

A feedback loop connects the frontend to ground-truth collection and behavioural learning.

## 5. Database Changes

Three new ML-related database tables were introduced:

**ml_ground_truth**
- User confirmations and corrections.
- Original anomaly scores.
- Reviewer notes.
- Timestamps and feedback records.

**ml_behavioral_profiles**
- Workspace-specific category and merchant profiles.
- Statistical baselines.
- Profile update timestamps.

**ml_model_registry**
- Model versions.
- Model status.
- Hyperparameters.
- Evaluation metrics.

The transactions table was also extended with:

- `anomaly_explanation`
- `anomaly_feedback_status`

SQLite schema updates are handled during application startup.
